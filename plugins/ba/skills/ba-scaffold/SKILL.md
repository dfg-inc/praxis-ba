# BA Scaffold — слой проекта вокруг канона

Разворачивает **папки и стартовые документы проекта**, которых движок `praxis-ba` не создаёт и не видит. Существует затем, чтобы агент не начинал работу на пустом контексте: без `project.md`, глоссария и карты первоисточников требования пишутся из воздуха.

**Вход:** slug проекта + подтверждение человека.
**Выход:** скелет папки проекта, готовый под элиситацию (`praxis-ba:capture-cr`) или под реверс существующего кода (`ba-onboard`).

<HARD-GATE>
(1) Не создавай `canon/` руками и не пиши в него — это территория движка, любая запись туда идёт только через скиллы `praxis-ba`. (2) Ничего не перезаписывай: существующий файл или папку пропускай, о расхождениях сообщай. (3) Не разворачивай скелет без подтверждения человека и без slug.
</HARD-GATE>

## Два слоя, и их нельзя путать

| Слой | Кто владеет | Что внутри |
|---|---|---|
| `canon/` | движок `praxis-ba` | vision, epics, fr/nfr, br, cr, wp, bug — только через его скиллы и CLI |
| всё остальное | ты и человек | первоисточники, справочники, диаграммы, встречи, задачи, архив |

Движок канон валидирует и форматирует; слой вокруг него он **не видит вообще** — ни `validate`, ни `fmt` его не касаются. Поэтому связность этого слоя держим сами: относительные ссылки + `ba-lint`.

## Checklist

1. **Спроси slug** проекта и подтверждение на развёртывание. Если папка проекта уже есть — покажи, чего в ней не хватает, и разворачивай только недостающее.
2. **Проверь, что есть.** Пройди по составу ниже, отметь присутствующее.
3. **Разверни недостающее** из `${CLAUDE_PLUGIN_ROOT}/templates/layer/`, подставив `project` = slug и текущую дату. Соответствие простое: имя файла шаблона = имя целевого файла, кроме двух: `inputs-readme.md` → `inputs/README.md` и `nfr-catalog.md` → `shared/nfr.md`. Шаблоны страниц канона (`fr`, `nfr`, `br`, `cr`, `wp`, `vision`, `epic-index`) лежат уровнем выше, в `templates/`, и этим скиллом не используются: канон разворачивают скиллы движка. `taxonomy.md` копируется как есть — словарь тегов один на все проекты, поле `project` в нём остаётся пустым.
4. **Наполни ядро `project.md`** — тремя короткими вопросами (ниже), не выспрашивая всё остальное.
5. **Заполни карту первоисточников** `inputs/README.md`: откуда взят каждый документ, что внутри, чему верить. Соглашения — в самом шаблоне, они не косметические: чаще всего проект спотыкается о два похожих документа от разных сторон и о ссылку на версию, которая через месяц уже про другое.
6. **Покажи результат** списком созданного и скажи, какой скилл дальше: есть код без требований → `ba-onboard`; есть документы-первоисточники → `praxis-ba:capture-cr`.

## Состав скелета

```
<проект>/
  project.md          ← контекст продукта: суть, пользователи, цели, регуляторный контур
  glossary.md         ← термины предметной области
  CLAUDE.md           ← конвенции проекта для агента (пишется вручную, шаблона нет)
  inputs/             ← сырьё и первоисточники, ТОЛЬКО на чтение
    README.md         ← карта: что откуда взято и чему верить
  shared/             ← справочники, общие для всех срезов
    nfr.md            ← каталог НФР (на него ссылаются требования канона)
    taxonomy.md       ← словарь тегов (проверяется ba-lint)
    rbac.md           ← ролевая модель
    stakeholders.md   ← стороны и их интересы
    data-model.md     ← сущности и их поля, на BA-уровне
    integrations.md   ← внешние системы и обмен
  diagrams/           ← диаграммы (последовательности, use-case, схемы)
  meetings/           ← встречи, вопросы по адресатам, action items
  tasks/              ← задачи исполнителям и рабочие файлы (impacts, черновики нарезки)
  archive/            ← устаревшее; НЕ источник и НЕ объект ссылок
  canon/              ← движок; создаётся скиллами praxis-ba, не здесь
```

Папки без файлов создавай с `.gitkeep` — пустая папка в git не сохраняется.

**`shared/` обязана лежать рядом с каноном или внутри него.** `praxis-ba validate` ищет словарь тегов и каталог НФР по двум путям: `<repo>/shared/` и `<на уровень выше repo>/shared/`. Если справочники окажутся в другом месте, проверка тегов и проверка ссылок на каталог НФР пропускаются с advisory-пометкой — не молча «всё зелёное без проверки».

**Чего в скелете сознательно нет.** Папок `features/`, `stories/`, `business-rules/` — это раскладка старого RPIV-флоу до подключения движка. Требования теперь живут в `canon/` (FR и NFR внутри папки эпика, BR плоско в `canon/br/`), и вторая раскладка рядом означает два конкурирующих места для одного требования. Если в проекте такие папки остались с прежних времён — предложи человеку перенести их в `archive/`, сам не переноси.

## Ядро project.md — три вопроса

Задавай по одному, только если `project.md` ещё заглушка:

1. **Что за продукт и какую задачу он решает?** → секция «Суть продукта».
2. **Кто основные пользователи и в чём ценность?** → «Пользователи», «Цели и ценность».
3. **Ключ проекта (2–4 буквы, как в трекере)?** → поле `project_key` во frontmatter.

`stakeholders.md`, `rbac.md` и `shared/*` целиком на этом шаге не требуй — они наполняются по ходу: из первоисточников, из интервью по CR, из реверса кода.

**Регуляторный контур объявляет человек.** Юрисдикция и применимые регуляции — блок в `project.md`; из кода и из документов подрядчика они не выводятся. Не оставляй его пустым молча — либо ответ человека, либо `[NEEDS CLARIFICATION]`.

## Правила

- **Не перезаписывать** — скелет доразворачивается, а не пересобирается.
- **Один документ — одна актуальная версия.** Черновики и прошлые редакции — в `archive/`, не рядом в корне.
- **Папка — связная сеть относительных ссылок.** Переименовал или перенёс файл — обнови ссылки на него и прогони `ba-lint`.
- **`inputs/` только на чтение.** Первоисточник не правится под удобство: расхождения фиксируются в `meetings/`, а не затиранием сырья.
- **Технологии — не термины.** Названия фреймворков и полей БД держи в отдельном тех-словаре, в требования и глоссарий не тащи.
